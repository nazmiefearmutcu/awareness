## 1. Postgres mode — parity verdict

**Docker is NOT available on this machine** — `docker info` fails (no daemon socket), no
Docker Desktop / colima / `dockerd`, and no local `postgres`/`psql` binaries. `docker compose up`
was therefore **not** run — no containers were started and none are left running.

**Fallback: full code-level parity audit of every sqlite-vs-postgres branch in
`src/awareness/storage/state.py`** (plus a live SQLite exercise of every flow to anchor the
comparison, and the repo's own Postgres-parity test suites — all pass).

### 1a. Live SQLite exercise (baseline behavior — all 12 flows, 0.25 s)

Script: `state_exercise.py` against `sqlite:///…/state_exercise.sqlite` (WAL).

| Flow | Result (SQLite) |
|---|---|
| init() ×2 (idempotency) | ok — second init raises nothing |
| create_job / get_job | ok |
| add_tasks(12) then re-add 3 | 12 inserted, re-add inserted 0 (re-arms, keeps attempts) |
| claim — 4 threads × limit 3 | 12 unique claims, **zero overlap** (invariant held) |
| complete + counters + checkpoint | tasks_completed incremented; checkpoint round-trips |
| dedup upsert ×2 same hash | `(doc-1, was_new=True)` → `(doc-1, was_new=False)`; capture_count bumped |
| near-dup band insert + find | exact sig found; hamming-distance-1 neighbor also found |
| requeue orphans | 1 stale RUNNING → PENDING; backoff tasks counted (1) |
| DLQ add/list/replay/purge | 2 rows; timestamps ISO UTC `+00:00`; replay re-arms + decrements counter |
| tail_state set/get + dead-pid reconcile | running↔stopped; dead PID → cleared + job CANCELLED |
| reaper cleanup_old_tasks(0) | completed rows deleted; running/pending intact |
| manifest upsert / robots cache / url-fetch gate | ok |

**Divergence D1 — SQLite claim under-claim:** in the 4-thread claim round only **2 of 4
threads won claims in the first pass** (`[3,3,0,0]` — 6 of 12). Cause: SQLite SELECT is
unlocked; a thread's candidate SELECT returned rows that another thread's `UPDATE …
RETURNING` had already re-armed, so the guarded UPDATE (re-checks `status='pending'`)
matched 0 rows. The claim invariant held (no double-claim), but the first pass under-claims.
On Postgres this race is closed by `with_for_update(skip_locked=True)`, which locks the
SELECTed rows in-transaction, so the UPDATE is guaranteed to match and the full limit is
claimed per round. **Workaround (unchanged): workers loop on SQLite; they get the full
batch on PG.** Not a bug — a documented behavioral difference, parity-verified.

**Divergence D2 — process-local RLock in `requeue_orphaned_running`:** the requeue
serializes with a **process-local** `threading.RLock`. Safe for threads; with two workers
against the same PG DB, both can read the same orphan as RUNNING and both write — the DLQ
insert for a dead-lettered orphan could then duplicate (no unique key on `dlq`).

> **Resolution (D2)** — `dlq` now carries a **unique index `uq_dlq_task` on `task_id`**
> (created for both SQLite and PG, including legacy-DB migration) and `add_dlq` is
> conflict-tolerant (`ON CONFLICT (task_id) DO NOTHING`) — concurrent dead-letter inserts
> dedupe instead of duplicating. **Fixed in `876dbc6`.**

**Divergence D3 — PG engine pool sizing:** the PG engine had no `pool_pre_ping` and default
QueuePool(5 + 10 overflow), risking stale connections and "QueuePool limit reached" under
15+ concurrent worker threads.

> **Resolution (D3)** — PG engine now sets `pool_pre_ping=True` and `pool_size=10`
> (SQLite's single-file pool untouched). **Fixed in `876dbc6`.**

**Divergence D4 — remote-PID reconcile semantics (open, ops note):** `os.kill(pid,0)`
liveness is same-host-only; against a remote PG a live tail would be reconciled as dead
(phantom CANCELLED jobs). Gate reconcile on a host/instance id in `tail_state` if remote PG
becomes a deployment target.

**Engine/driver note:** `postgresql+asyncpg://` works in sync mode only via greenlet
emulation — slower and unnecessary here; the compose-documented
`postgresql+psycopg://` is the natural driver. `asyncpg`/`psycopg` live in the `postgres`
extra (`pyproject.toml`), not the frozen default install — a PG deploy needs
`pip install -e '.[postgres]'`.

**Verdict: postgres mode is well-implemented** — every PG branch is syntactically/
semantically correct, the C-07 migration parity regression is covered by tests, and no
PG-blocking bug was found in static audit. The two actionable gaps found (D2 DLQ
duplication, D3 pool sizing) are fixed in `876dbc6`; the remaining items (D4 remote-PID,
full-db VACUUM) are operational notes. Live PG execution remains unverified (no
docker/postgres on this host).
